# Regex, small model or LLM?

A measured answer on one real task: spotting the messages in which I correct my
own AI assistant.

I run Hermès, a fleet of about sixty scheduled agents that work for me every
day. I talk to it on Telegram, and when it gets something wrong I say so: a
reproach, a standing instruction ("never do X", "always Y"), or a pointer to its
mistake. Those corrections are worth catching, because a weekly agent turns them into
durable rules. In production a regex catches the obvious ones and Claude Haiku
reads whatever the regex misses.

The question this repo answers with numbers: **is the LLM worth it here, or
would a classic model trained on my own messages do as well, faster and for
nothing?**

## What is compared

Five detectors, scored on the same gold-labeled set of 260 messages:

| Detector | What it is |
|---|---|
| `regex` | The production regular expression (French phrasings of a correction). |
| `haiku` | Claude Haiku 5.5 with the production prompt, called as in production (`claude -p`): one call per message. Three runs were made; the headline row is the first, the spread across runs is reported, and `haiku vote3` is the majority of the three, priced as three calls. |
| `pipeline` | Production as it runs: regex first, Haiku for the messages it does not flag. |
| `tfidf` | TF-IDF character and word n-grams with a logistic regression: the simplest machine-learning baseline. |
| `finetune` | `almanach/camembert-base` (a French RoBERTa) fine-tuned with PyTorch. |

Each model also runs in a `+prior` variant that sees the assistant's previous
reply, as Haiku does in production.

## Method

**Data.** A frozen snapshot of my Telegram chat log with the assistant, filtered
to what production actually classifies: slash commands removed, the previous
reply attached only if it came within 30 minutes (production keeps its first 500
characters and the prompt the last 300 of those), Haiku
only called on messages of at least 6 characters. 260 messages remain. **No
message is published here**, not even as an example: the repo holds the code,
the method and aggregate numbers only. `src/cdbench/privacy.py` fails the
report if any 30-character slice of a real message appears in `results/` or in
this README.

**Ground truth.** Claude Opus labeled all 260 messages, blind to the regex and
to Haiku (it sees the reference definition, the message and the previous
reply). I then arbitrated 80 messages myself on Telegram:

- 60 disagreements, by priority: the 39 messages where Opus contradicted Haiku,
  the 19 where Opus reported a confidence under 0.7, and 2 of the 35 where Opus
  contradicted only the regex. The other 33 kept their Opus label;
- 20 messages drawn at random among those where everyone agreed. They measure
  how often Opus is wrong when nobody contradicts it, the error that would
  flatter Haiku. The rate comes with a 95 % Wilson interval: with 20 messages,
  even zero errors leaves room for about one in six.

**Evaluation.** Stratified 5-fold cross-validation (seed 20261026). The two
trained models never see their test fold: the logistic regression's
regularisation is tuned by an inner 3-fold search on the training folds, and
the fine-tuned model uses fixed hyperparameters (6 epochs, learning rate 3e-5,
batch 16, class-weighted loss, linear schedule with 10 % warmup). Every score
comes with a 95 % bootstrap interval over messages.

**Cost.** Haiku is priced at the public API list price ($0.10 per million input
tokens, $0.50 per million output tokens, read on 2026-10-26). Two figures are
given: a **direct API call** (the detection prompt only, what a product would
send) and **the production path** (`claude -p` adds about 2,500 tokens of its
own system prompt, cached, around a prompt of about 150). Local models cost
nothing beyond the machine.

**Latency.** Haiku as measured through `claude -p`, including process start.
Local models on an Apple M1 Max, one message at a time, on the GPU (MPS) and on
the CPU.

### What I conclude

**Here, the LLM is worth it, but not for the reason usually given.** Haiku is the best
detector and costs about five cents per thousand messages at API price: at my volume
(260 messages in five months), about three cents a year. Cost and latency decide
nothing at this scale; quality does.

**The simple baseline is not far behind.** A TF-IDF logistic regression trained on
about 200 examples lands 0.09 F1 below Haiku; the paired interval excludes a tie, but
only just. It answers in about a millisecond, for free, without sending anything out.
With a few hundred more labels, millions of messages a day, or data that must not leave
the machine, it would be the right choice.

**Fine-tuning a 110-million-parameter model on 200 examples does not beat TF-IDF.** It
learns surface cues: long task requests that mention an email or a name read to it as
reproaches. Giving the trained models the assistant's previous reply makes TF-IDF
clearly worse and probably the fine-tuned model too (the reply's vocabulary drowns the
message's); Haiku reads the same context without losing anything.

**The production pipeline can drop its regex.** The regex is precise but finds only a
fifth of the corrections, and Haiku with context finds 19 of its 20. In front of Haiku,
it added one correction and three false alarms.

**The ceiling is not the model.** About half of Haiku's misses are corrections that
exist only through the conversation: a short follow-up after the assistant failed, a
pointer back to an earlier screenshot, a reminder that something was already done. No
detector reading one message and the end of the previous reply can see them. The other
limit is the task itself: see the label agreement below.

## Limits

- **One person, one language, one task.** 260 messages, 92 corrections.
  Intervals are wide on purpose: do not read a 0.03 gap as a result.
- **The ground truth starts from an LLM, and the review favours the production
  detectors.** Opus labeled first and I arbitrated 80 messages. Opus errors were
  only looked for where Opus clashed with Haiku or the regex, so those two get
  their disagreements corrected while the trained models get no such check.
- **Even I do not draw the line in the same place twice.** On the 20 messages drawn
  where Opus, the regex and Haiku all agreed, I overruled Opus 4 times (20 %, Wilson
  95 % interval 8 % to 42 %). Three were bare follow-ups after a failure, which I count
  as corrections and the written definition does not clearly cover. My own labels are
  not fully consistent either. So the 180 labels I did not review likely hold a
  comparable share of disagreements, which flatter Haiku (it agreed with them) and
  blur the training data of the other two models. Past about 0.8 F1, this benchmark
  measures annotator agreement more than detector quality.
- **Haiku's latency** was measured through `claude -p` with four calls running
  at once, process start included; a direct API call is faster. Answers that
  were neither "correction" nor "other" count as "other", as in production; the
  count is in `results/summary.json`.
- **The fine-tuned model is not bit-for-bit reproducible.** Training on the Apple GPU
  is not deterministic even with fixed seeds: three runs of the same code gave F1
  0.62, 0.64 and 0.65. The table shows the last run; read its row to about ±0.02.
- **Small training sets favour the LLM.** A fine-tuned model sees about 200
  examples per fold. The point is the question a team faces on day one, not the
  ceiling of each approach.

## Rerun it on your own data

```bash
uv sync
uv run cdbench snapshot --chat-log path/to/chat.jsonl --data-dir path/to/private
uv run cdbench label --data-dir path/to/private
uv run cdbench select-review --data-dir path/to/private
# fill path/to/private/answers.json: {"<message id>": true | false}
uv run cdbench merge-gold --data-dir path/to/private
uv run cdbench run-haiku --data-dir path/to/private
uv run cdbench evaluate --data-dir path/to/private --finetune-model path/to/camembert-base
```

The chat log is JSON lines with `ts`, `user_msg`, `assistant_reply` and
`tg_update_id`. Labeling and Haiku use the Claude Code CLI (`claude -p`).
`scripts/telegram_review.py` is how I did the arbitration from my phone; it
depends on my own setup and is optional. Models can be fetched once with `curl`
from Hugging Face and passed as a local directory.

The production regex and prompt are frozen copies; see [PROVENANCE.md](PROVENANCE.md).
